# 協議

[简体中文](protocol.md) | **繁體中文** | [English](protocol.en.md)

> 這份由 `scripts/docs.ts` 從簡體中文版自動轉換，改內容請改簡體中文版。

整個系統是一個迴圈，三個口子。

```
          事件                領活
  來源 ─────────▶  中控台  ◀───────── 接單程式 ── Agent
                   ▲ │
              回答 │ │ 卡片
                   │ ▼
                  通道 ◀──▶ 你
```

**中控台的核心不主動連線任何東西。** 來源、接單程式、通道都是它們自己連進來：核心不用知道它們在哪、用什麼語言寫、是哪家的產品，也不保管它們的憑證；你的電腦不用開放任何埠。協議就是下面這份 HTTP + JSON，寫一個新外掛只要會發 HTTP 請求。

一台電腦上用時，一條命令把三樣都跑在一個行程裡，它們之間照樣走這份協議。

**中控台沒有介面。** 你和它打交道靠通道和命令列。想要一個頁面或大屏，用「本人」一節的幾個請求自己做，它和命令列是同等的客戶端。

## 六個詞

| 詞       | 是什麼                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------ |
| **事件** | 發生了一件事：來源、編號、型別、對象、一句話、詳情、回原處的連結。時間到了是事件，你點了卡片也是事件。                   |
| **規則** | 寫在 `rules.json` 裡：什麼事件，交給哪個 Agent，在哪個目錄，用哪個 Skill，什麼時候告訴你。                               |
| **事項** | 同一條規則下同一個對象的事。事件歸進事項，卡片、到期複查、會話都掛在事項上。規則沒寫 `parallel` 時，整條規則是一個事項。 |
| **一輪** | 一次執行：領一批事件，交一份回條，然後結束。一輪會結束，事項會繼續。                                                     |
| **回條** | Agent 的最後一條訊息。它想讓中控台做的事全寫在這裡，這一輪結束時在一個交易裡一次生效。                                     |
| **卡片** | 給你看的東西。帶選項的是提問，你選了就是一條新事件，事項接著往前走；不帶選項的是通知。                                   |

## 六條原則

1. **注意力最貴。** 預設安靜。沒事不說話，能自己做的自己做完，只有規則寫明要先問的事、確實需要本人解除的阻塞才打斷你。
2. **一切都是事件。** 外部系統、時間、到期複查、你的決定，走的是同一條路。
3. **一切都連進來。** 核心沒有對外的請求。憑證留在用它的地方，出事的範圍也留在那裡。
4. **Agent 就是一個行程。** 給它提示詞，它印出最後一條訊息。Claude Code、Codex、任何命令列 Agent、一段腳本、一條 CI 流水線都一樣，不需要 SDK。要啟動遠端工作的行程，負責跟到真正做完才退出。
5. **一輪不等人。** 要問你就結束這一輪，收到回答後再開始處理，儘量接著原來的會話。等你的時候不佔行程、不花 Token，重啟也不丟。
6. **規則才是指令。** 事件決定不了交給誰、在哪個目錄、用哪個 Skill、給什麼權限，這些只由規則決定。別人寫的話不進提示詞，只放進標明“是資料”的檔案。這擋不住所有提示注入，但把最壞的結果限制在規則給定的範圍裡。

## 規則

```jsonc
{
  "timezone": "Asia/Shanghai", // 定時和“今天”用的時區，預設系統時區
  "language": "zh-CN", // 介面、卡片和給 Agent 的提示詞用的語言：zh-CN（預設）、zh-TW 或 en
  "askFirst": ["刪資料", "停服", "花錢", "對外發訊息"], // 只有這幾類事 Agent 才先問你
  "sources": { "shop": { "name": "shop" }, "github": { "name": "GitHub", "adapter": "github" } },
  "agents": {
    "claude": {
      "name": "Claude Code",
      "worker": "mac-mini",
      "use": "claude",
      "model": "…",
      "effort": "high",
      "access": "edit",
    },
    "cursor": {
      "name": "Cursor",
      "worker": "mac-mini",
      "use": "command",
      "command": ["agent", "-p", "--trust", "{prompt}"],
    },
  },
  "channels": { "feishu": { "name": "飛書", "answerers": ["ou_xxx"] } },
  "rules": [
    {
      "name": "處理告警",
      "when": { "source": "shop", "types": ["alert.*"] }, // 或 { "cron": "0 9 * * *" }
      "to": "claude",
      "cwd": "~/code/shop",
      "skill": "run-ops",
      "prompt": "按其中……一節處理。",
      "group": "ops", // 同一組一次一輪，預設就是規則名
      "parallel": 3, // 寫了就按對象分事項：同一對象一次一輪，這一組最多 3 輪，還受接單程式的 worker.capacity 限制（預設 2）
      "resume": true, // 同一事項的新事件接著上一輪的會話，預設每次開新會話
      "tell": "needed", // always 每輪做成都發（沒事可做、沒跑成不發）/ needed 只在有卡片時（預設）/ never 只壓住回條裡的通知，提問和中控台自己的告警照發
      "emits": { "source": "shop", "types": ["pr.*"] }, // 回條裡能發什麼事件，不寫就不能發
      "channels": ["feishu"], // 這條規則的卡片和通知只發到這幾個通道，不寫就發到所有通道
    },
  ],
  "elsewhere": [
    {
      "name": "每週清理",
      "source": "shop",
      "to": "claude",
      "cron": "0 6 * * 0",
      "where": "Claude 應用的定時任務",
      "cwd": "~/code/shop",
      "skill": "weekly-sweep",
      "prompt": "按其中“回答來了”一節處理。", // 可選：要問你時寫，回答後在這裡照這個接著做
    },
  ],
}
```

`language` 決定中控台自己寫的字（卡片、錯誤、命令列輸出、卡片頁面）用哪種語言，也隨每一輪的 Job 交給接單程式，讓 Agent 用這種語言寫結論和卡片；卡片也帶著它，通道自己的字照它顯示。不寫就是簡體中文，和以前一樣。日誌裡已有的卡片保留當時的文字，不重寫。`agent-autoloop init --language zh-TW`（或環境變數 `AGENT_AUTOLOOP_LANGUAGE`）在新的 `rules.json` 裡寫好它；用安裝命令新裝時，按這台電腦的 `LANG` 選：`zh_TW`、`zh_HK`、`zh_MO` 是繁體，其他中文是簡體，別的都是英文。老外掛和客戶端不認識這個欄位，忽略即可。

`elsewhere` 是在別處定時跑的任務：中控台不啟動它們，只在 `agent-autoloop status` 裡列出來，它們要找你時用 `POST /v1/tell`。寫了 `cwd`（還要寫 `skill` 或 `prompt`）的也能問你：卡片帶選項，你答了，中控台像規則的一輪那樣叫醒 `to`，在 `cwd` 照 `skill`、`prompt` 接著做，這一輪的組就是任務名，一次一輪，不接定時任務自己的會話。規則寫錯了，檔案改動不生效，舊規則繼續跑，並推一張卡片告訴你錯在哪。

寫了 `resume`，一輪開始時如果事項的上一輪做完了（包括沒事可做）、留下了會話，就接著那個會話；會話越接越長，Token 和費用也會跟著漲。這幾種情況開新會話：上一輪被停掉了（你停的，或連續失敗停下的），接著它多半還是同樣的結果；上一輪是別的 Agent 跑的；上一輪沒有會話。沒寫 `parallel` 時整條規則是一個事項，所有事件接同一個會話；事件不帶 `subject` 時也都算同一個事項。回答和到期的複查仍回到提問和約定時的會話，重派的也留在自己的會話。

不管寫沒寫 `resume`，一輪要接的會話裡如果還有別的輪次沒結束，或者沒了音信、可能還在跑，這一輪就開新會話，不讓兩個行程開同一個會話；回答和複查的內容照樣帶給它。

排隊和等待重試的任務在領取時一起採用最新的 Agent、目錄、提示詞和權限；換了 Agent 就不帶舊 Agent 的會話。已經領取的任務保留領取時的 Job 設定和接單程式，重複 claim、心跳、停止和重啟恢復都不隨規則更新換人。事件已經歸屬的事項不重新拆分或合併，回答和到期的複查回到提問和約定時的事項，規則後來去掉 `parallel` 也一樣；回條中的事件許可和通知方式仍按提交時的規則核驗。

## 來源：把世界變成事件

```
POST /v1/events                    Authorization: Bearer <來源的金鑰>
{ "id": "12:new", "type": "feedback.new", "subject": "#12", "summary": "…", "detail": "…", "link": "https://…" }
→ 200 { "event": 34, "duplicate": false, "routed": ["處理意見"] }
```

- `id` 和 `type` 必填。同一來源同一 `id` 只記一次，所以來源儘管重發。
- `subject` 只能是識別符號（字母、數字和 `# . _ : / @ -`），`link` 只能是純 ASCII 網址，因為它們會進提示詞。`summary`、`detail` 不進提示詞。
- 沒有規則匹配的事件也留著，`agent-autoloop status` 看得到。
- 欄位上限：`id` 200 個字、`subject` 100、`summary` 200、`detail` 4000、`link` 500，`type` 64 個字元。

三種別的進法，到中控台都是同一種事件：

- **定時**：規則寫 `cron`。錯過的（比如電腦合蓋了）醒來只補最近的一次。重複的時刻（夏令時）只跑第一次，不存在的時刻跳過。
- **別人家的 Webhook**：`POST /v1/in/<來源>`。來源配了 `adapter`，就交給 `plugins/<adapter>/source.ts` 裡的函式驗籤、翻譯成事件，它只翻譯，不發請求。驗籤用的秘密放在 `secrets.env` 的 `AGENT_AUTOLOOP_SECRET_<來源>`（來源名轉大寫，`-` 換成 `_`，改完重啟中控台），不進 `rules.json`。
- **輪詢**：不用連公網，沒新東西不花 Token。規則定時叫一段腳本（也是一個 Agent），腳本在回條的 `events` 裡交回新事件。事件的 `id` 要穩定，讀的範圍可以重疊，中控台會去重；腳本要在回條交出去之後才推進自己的游標，或者乾脆不留游標。

來源或 `elsewhere` 任務有話要直接告訴你（不用 Agent 處理）：

```
POST /v1/tell    { "key": "weekly-44", "text": "…" }              Authorization: Bearer <來源的金鑰>
POST /v1/tell    { "task": "每週清理", "key": "x", "text": "…" }   Authorization: Bearer <接單程式的金鑰>
→ 200 { "card": 56, "duplicate": false }
```

這樣說的是僅告知的通知（`fyi`），沒有按鈕，同一個 `key` 只發一次。寫了 `cwd` 的 `elsewhere` 任務要你拍板時，用 `ask` 代替 `key` 和 `text`，內容和回條裡的 `ask` 一樣：

```
POST /v1/tell    { "task": "每週清理", "ask": { "title", "text", "options": ["…", "…"], "recommend": 0, "about": "…", "key": "…" } }
                                                                    Authorization: Bearer <接單程式的金鑰>
→ 200 { "card": 57, "duplicate": false }
```

同一個 `key`（不寫就按標題和內容）的卡片還開著就不再發。你答了，中控台叫醒這個任務的 Agent 在 `cwd` 接著做，回答在這一輪的 `answers` 裡；做完卡片改成已執行。沒寫 `cwd` 的任務問你返回 400。老中控台不認識 `ask`，會返回 400：中控台和接單程式分開部署時先升中控台。

## Agent：領活、幹活、交回條

每台電腦上有一個接單程式，它只往外連。一台接單程式可以服務多個 Agent。

```
GET /v1/work?claim=<這次領活的編號>&wait=50&running=7,8&capacity=1    Authorization: Bearer <接單程式的金鑰>
→ 200 { "job": null | Job, "cancel": [7] }
```

- 沒活時最多等 `wait` 秒，新活一來立即返回。`running` 是手上在跑的，同時也是心跳。`capacity=0` 只報到、不領活。
- 手上有活時可以每秒來問活、查取消。心跳最多一分鐘記進日誌一次，手上有幾輪都只記一條；通道領卡片也一樣。所以 `/v1/state` 的 `seenAt` 可能比最後一次來的時間早不到一分鐘，“5 分鐘沒報”“10 分鐘沒連上”也可能因此提前不到一分鐘判斷；`online` 留了這一分鐘的餘量，記錄後 3 分鐘內都算線上。
- 響應丟了，用同一個 `claim` 再來一次，拿回的是同一份活。
- `cancel` 是要停掉的。接單程式先向整個行程組發停止訊號，10 秒後仍有行程執行就強制結束；確認組內沒有活行程後才交 `outcome: "cancelled"`，這個事項才放開。停止期間重啟接單程式也繼續這一步。要停的這一輪交回 `failed` 也算停了，不再重試。

```jsonc
// Job：一輪的全部。token 只對這一輪的這一次執行有效。
{
  "run": 12, "token": "…", "attempt": 1,
  "rule": { "name": "處理告警", "cwd": "~/code/shop", "skill": "run-ops", "prompt": "按其中……處理。" },
  "agent": { "id": "claude", "name": "Claude Code", "use": "claude", "model": "…", "effort": "high", "access": "edit" },
  "session": null,       // 儘量接著的會話：重派時是上一次的，回答來了是提問那一輪的，規則寫了 resume 時是這個事項上一輪的。接不上就開新的，所以它只是最佳化
  "askFirst": ["刪資料", "…"],
  "language": "zh-CN",   // 規則的語言。老中控台不給，就當簡體中文
  "context": {           // 接單程式把它寫成檔案交給 Agent，都是資料
    "events":  [{ "id", "source", "sourceName", "type", "subject", "summary", "detail", "link", "receivedAt" }],
    "answers": [{ "card", "title", "options", "choice", "text", "about", "by", "at" }],  // 這一輪要接著做的決定
    "timers":  [{ "key", "about", "at" }],                                               // 這一輪到期的複查
    "waiting": [{ "key", "about", "at" }],                                               // 這個事項還沒到期的複查
    "open":    [{ "card", "title", "text", "at" }],                                      // 同來源同組還沒收尾的卡片
    "decided": [{ "card", "title", "choice", "at" }]                                     // 這個事項定過的事，只對當時那件事有效
  }
}
```

```
POST /v1/runs/12/started   Authorization: Bearer <token>   { "session": "…", "link": "claude://…" }
POST /v1/runs/12/result    Authorization: Bearer <token>   Result
→ 200 { "rejected": [{ "card": 9, "reason": "不在本輪核對範圍" }] }
```

```jsonc
// Result
{
  "outcome": "done" | "nothing" | "failed" | "cancelled",
  "summary": "一句話", "error": "沒跑成的原因", "session": "…",
  "usage": { "input": 0, "output": 0, "cached": 0, "cost": 0 },
  // 下面就是回條，一個交易裡一次生效
  "ask":     [{ "title", "text", "options": ["…", "…"], "recommend": 0, "about": "留給接著乾的自己", "key": "這件事的固定名字" }],
  "notice":  [{ "title", "text", "key", "fyi": true }],
  "resolve": [{ "card": 3, "reason": "在哪核實了已解決" }],
  "later":   [{ "key": "…", "at": "2026-11-05T09:00:00+08:00", "about": "到時候查什麼" }, { "key": "…", "cancel": true }],
  "events":  [{ "id", "type", "subject", "summary", "detail", "link" }]
}
```

- 結果可以重放：響應丟了，同一個 token 再交一次同樣的內容，得到同樣的確認；內容不同返回 409。
- `failed` 會重派，所以它只帶 `notice`，其餘的不生效；本人要停的這一輪交 `failed` 不再重派，`notice` 也不生效。
- 需要本人恢復連線、登入或身份驗證時，用 `done` 結束本輪並交 `ask`，不交 `failed`。`done` 表示本輪結束，未完成的事項由卡片繼續跟進，不代表網頁已經驗收。同一阻塞已有 `open` 卡片時不重複提問，不用 `later` 定時重試；`waiting` 裡同一阻塞已有的複查用 `cancel` 取消。保留已完成業務，`about` 寫清恢復後只做哪些剩餘步驟。
- `usage` 由接單程式上報本次執行的用量，包含這次執行的回條重寫；每一項都可以沒有：`input`、`output`、`cached` 是 Token 數，`cost` 是美元。中控台把同一輪各次執行的已報數值相加，重複提交不重複計費；沒有上報的欄位保持預設，不當成零。`agent-autoloop status` 按完成時間彙總今天和最近 7 天已結束的輪次，沒上報的輪數如實寫出來。
- 有的 Agent 只給會話累計值（Codex 的 Token、Claude Code 的費用）。接單程式減去這次啟動前的累計值再上報，所以這裡總是本次的量；沒有記錄的續接不報這幾項，詳見[外掛說明](plugins.zh-TW.md#agent-外掛)。
- `ask` 的 `key` 範圍是這個事項：同一個 `key` 的卡片還開著就不再發。關掉之後再問是新的一次。
- `notice` 可選填布林欄位 `fyi`：`true` 表示「僅告知」，卡片建立時就是 `closed`，仍會在建立後的 24 小時內投遞，飛書顯示灰卡、不帶「已處理」按鈕；不會進入後續輪次的 `open`，點選也不會產生回答事件。省略或填 `false` 時，通知帶「已處理」按鈕，也能被 `resolve` 結案。它一建立就結案了，所以同一個 `key` 下一輪再寫還會再發一張；同一輪重試只發一次。規則寫了 `tell: "never"` 時照樣不發。老中控台不認識這個欄位，會拒收整份回條：中控台和接單程式分開部署時先升中控台。
- `resolve` 只能結同來源、同組、這一輪領活前就有的卡片，越界的寫進 `rejected`，不影響這一輪的結果。
- `later` 的 `key` 範圍是這個事項，同一個 `key` 再寫一次就是改時間。
- `events` 的來源由規則的 `emits` 決定，回條改不了。

### Agent 只需要做一件事

接單程式把提示詞交給 Agent，Agent 的最後一條訊息就是回條：

````
第一行一句話結論。可自動重試的臨時失敗寫「沒跑成：原因」，需要本人恢復的阻塞寫「待你處理：原因」並交 ask，沒事可做寫「沒事可做：原因」。其餘結束本輪，事項由回條繼續跟進。

```agent-autoloop
{ "ask": [ … ], "notice": [ … ], "resolve": [ … ], "later": [ … ], "events": [ … ] }
```
````

第一行的「沒跑成」「沒事可做」也認繁體的「沒跑成」「沒事可做」和英文的 `FAILED`、`NOTHING`。

程式碼塊可有可無。Agent 不需要裝任何東西、不需要連中控台，所以沙箱裡的、雲端的 Agent 也能接。

回條寫錯不重做業務：接單程式接著原會話，只讓它把最後一條訊息重寫一遍，最多兩次；沒有會話的 Agent（比如 `command`）不重寫，直接走下面這句。還是讀不懂，或重寫行程啟動失敗、報錯、超時、沒有輸出，就保留原業務訊息第一行的結局，回條作廢，推一張卡片告訴你原文在哪（每一輪的輸出在這一輪結束後留 14 天）；補回條失敗不會把已完成的業務變成自動重試。

### 接一個新 Agent

規則裡寫一行，任何能印出最後一條訊息的命令都行，退出碼不是 0 就算沒跑成：

```json
{ "name": "Hermes", "worker": "mac-mini", "use": "command", "command": ["hermes", "chat", "-Q", "-q", "{prompt}"] }
```

想要會話接續、開啟會話的連結、用量統計，就在 `plugins/<名字>/agent.ts` 寫一個檔案（見 `plugins/claude/agent.ts`）：

```ts
export default {
  command: (run) => [...],                                         // 這一輪的命令列，run.resume 是要接著的會話
  read: (output) => ({ text, session, usage, finished, started }), // 從輸出裡讀出最後一條訊息和會話
  link: (session) => "…",                                          // 可選：開啟這個會話的連結
};
```

`started` 表示 Agent 已經收下這一輪的提示詞，無論後來跑完、出錯還是行程沒了都要帶上。帶了它，這一輪再出錯就算沒跑成，留在原會話由中控台重派；不帶，接著舊會話跑時的失敗都當成接不上，開新會話把提示詞再跑一遍。`finished` 表示這一輪真的結束了，過 30 秒還不退出就停掉它；後台任務還沒跑完、Agent 還要回來接著干時不算。

專用外掛的 `access` 三檔，翻譯成各自 CLI 的權限：`read` 只讀，`edit` 只改工作目錄（預設），`full` 完整權限、不審批。只讀不等於讀不到金鑰，要隔離金鑰請用系統帳號或容器。`command` 只傳命令參數，不替任意程式限制權限。

瀏覽器由 Agent 的執行環境提供。Codex 使用後台 `codex exec`，不能假定桌面應用的瀏覽器連線自動可用；使用該輪實際可用的瀏覽器工具，或規則、Skill 明確設定的入口。入口只處理網頁步驟並接續自己的會話，業務和回條仍由主任務負責。中控台不附帶瀏覽器橋接，不安裝或授權瀏覽器工具；接入驗收見[外掛說明](plugins.zh-TW.md#瀏覽器接入)。

## 通道：把卡片送到你面前

通道是一個往外連的小程式。

```
GET /v1/cards/next?wait=50    Authorization: Bearer <通道的金鑰>
→ 200 { "card": null | Card }

// Card：這張卡片現在的樣子。內容建立後不變，只有狀態會變
{ "id": 56, "version": 2, "ref": null, "kind": "ask", "state": "open",
  "title": "…", "text": "…", "options": ["…", "…"], "recommend": 0,
  "choice": null, "answer": null, "by": null, "result": null, "link": null, "language": "zh-CN" }
```

- `ref` 是空的就發一條新的；不是空的就把那條改成現在的樣子，改不了就直接報告。
- 發完報告：`POST /v1/cards/56/delivered { "version": 2, "ref": "om_xxx" }`。沒報告的過一分鐘會再給你。**支援冪等鍵的平台，發新訊息只用卡片編號，不帶版本**（飛書改不動已經結束的卡片時另發一條，這一條才帶版本）。平台不支援時無法保證去重，Webhook 範本可能在報告丟失後重發。
- 發不出去：`POST /v1/cards/56/failed { "version": 2, "error": "…" }`。第一次傳送隔得越來越久地重試，一小時後放棄（卡片還開著，`agent-autoloop status` 看得到）；通道一直沒來領不算在內。
- 還沒送達就已經解決的卡片不再打擾你；僅告知的 `fyi` 通知在建立後的 24 小時內仍可投遞。
- 你點了：`POST /v1/cards/56/answer { "choice": 1, "by": "ou_xxx", "ref": "om_xxx" }`。只有第一次算數，`by` 要在這個通道的 `answerers` 裡，`ref` 要和送達的那條一致。普通通知有一個“已處理”按鈕，點了就結案；也可以帶 `text` 寫一句處理說明，結案時存進卡片的 `answer`，卡面和 `/v1/state` 都看得到。僅告知的 `fyi` 通知沒有按鈕。

最小的通道只要十幾行：領卡片、發文字和 `link`、報告。`link` 只給配了 `"links": true` 的通道，其他通道這裡是 `null`。它開啟一個不跑腳本的普通表單頁，這張卡片的文字和按鈕都在上面，誰拿到連結誰就能答，從卡片建立起 7 天內有效，過期後也不再顯示卡片內容，適合只會發文字的群機器人、郵件。能發按鈕、能收回呼的通道（比如飛書）用按鈕，身份由平台核驗，更安全。一台電腦上用時 `link` 是本機地址，手機打不開，要手機批請把中控台放到有公網地址的機器上，並配好 `publicUrl`。

### 暫停、恢復、立即執行

```
POST /v1/rules/巡檢/pause      { "reason": "上游在修", "until": "2026-11-07T09:00:00+08:00" }   兩項都可以不寫
→ 200 { "changed": true, "rule": "巡檢", "paused": { "by": "owner", "reason": "上游在修", "since": "…", "until": "…" } }
POST /v1/rules/巡檢/resume     {}
→ 200 { "changed": true, "rule": "巡檢" }
POST /v1/rules/巡檢/run        { "subject": "#12", "reason": "看一眼" }                         兩項都可以不寫
→ 200 { "event": 88, "run": 41 }
```

只接受本人的金鑰。規則名按 URL 編碼放進路徑，請求體可以為空；不認識的欄位返回 400。沒有這條規則返回 404 `沒有這條規則：<名字>`；`elsewhere` 裡的任務返回 400，因為中控台不啟動它。

暫停和恢復是日誌裡的事實（種類 `pauseRule`、`resumeRule`），不改 `rules.json`；重啟、從日誌重建投影后照樣有效。`by` 是所用本人金鑰的名字。重複暫停只更新原因和 `until`，`since` 保留第一次的時間；原因和 `until` 都沒變時 `changed` 為 false，也不追加事實。`until` 要帶時區、晚於現在；到了這個時間中控台自動恢復，記一條 `tick` 事實。

規則暫停中被移出 `rules.json` 也照樣能恢復。

暫停期間：

- **定時規則**：到點直接跳過，不記事件，不積壓。`lines[].skippedAt` 是最近一次跳過的時刻。恢復（手動或到了 `until`）後不補跑暫停期間錯過的時刻，從恢復的那一刻起的下一個時刻照常跑；中控台在暫停期間睡著了也一樣。
- **事件規則**：事件照常記下，但這條規則不接、不派活；恢復後也不補接。事件的 `paused` 記著因為暫停沒接它的規則，`/v1/events` 的應答多一個 `paused` 列表，`routed` 只列真正接了的規則。最近 20 條這樣的事件在 `/v1/state` 的 `skipped` 裡。這類事件不算“沒有規則接的事件”。同一事件匹配的其他規則照常接。不補接是因為暫停常常是因為下游壞了或者要止損，事後一次性湧進來的活比漏掉的更難收拾；需要時用立即執行補一輪。
- **已經排隊的、等重試的、暫停期間收到回答或到期複查的這一輪**：留在佇列裡不派出去，恢復後照常領取，不丟回答。已經在跑的這一輪不受影響，要停用 `stop`。

立即執行走正常派活：記一條 `run.manual` 事件（定時規則的來源是 `schedule`，事件規則用它的 `when.source`），`summary` 是“<金鑰名> 手動執行”，`detail` 是 `reason`；`subject` 決定 `parallel` 規則的事項。同一事項已經有排隊的一輪時並進那一輪，並取消它的重試等待。這一輪的 `runs[].manual` 為 true。**暫停中的規則不能立即執行**，返回 409 `規則「…」暫停中，先恢復再手動執行`：暫停的意思是這條規則一件活都不派，手動執行也不例外，這樣“暫停了就不會再花錢、不會再對外動作”這一條沒有例外。要試跑就先恢復再執行。

`/v1/state` 裡每條規則（`lines[]`）多了 `paused`（生效中的暫停：`by`、`reason`、`since`、`until`，沒暫停是 `null`）和 `skippedAt`；頂層多了 `pauses`（所有生效中的暫停，每項帶規則名 `name`）和 `skipped`。舊客戶端忽略這些欄位即可。

命令列：`agent-autoloop pause <規則> [--reason 原因] [--until 時間]`、`resume <規則>`、`run <規則> [--subject 對象] [--reason 說明]`；`status` 列出暫停中的規則。

`agent-autoloop check [檔案]` 只讀檔案、校驗規則，不開啟中控台資料庫，也不把檔案載入中控台；不寫檔名就查 `rules.json`。可以先校驗一份草稿再換上去。`/v1/state` 一次給最近 60 輪，`?before=<nextBefore>` 翻更早的。

`/v1/state` 的 `spending.today`、`spending.week` 獨立於分頁，按規則時區的今天和過去 7 × 24 小時的完成時間彙總。每項含 `rounds`、`tokens`、`cost`、`missingTokens`、`missingCost`，後兩項是沒報對應用量的輪數；從未開始就取消的輪次不計入。

安裝與解除安裝不改變 HTTP 協議。`agent-autoloop --version` 顯示版本與提交；`agent-autoloop uninstall` 確認後移除自身程式、連結和服務，始終保留規則、金鑰和記錄；`--yes` 只跳過確認。

## 誰能做什麼

| 憑證             | 能做                                                        | 不能做                                 |
| ---------------- | ----------------------------------------------------------- | -------------------------------------- |
| 來源的金鑰       | 以自己的名義發事件、發訊息                                  | 冒充別的來源，領活                     |
| 接單程式的金鑰   | 領交給它的活；以交給它的 `elsewhere` 任務的名義發訊息、提問 | 碰別人的活，發事件                     |
| 一輪的 token     | 報告這一輪的這一次執行                                      | 碰別的輪次                             |
| 通道的金鑰       | 領卡片、報告、轉達 `answerers` 的回答                       | 其他一切                               |
| 帶權限的卡片連結 | 回答這一張卡片                                              | 其他一切                               |
| 本人的金鑰       | 看全部、回答、結案、停止，暫停、恢復、立即執行規則          | 發事件，領活，改規則（規則只在檔案裡） |

普通訪問金鑰只儲存 SHA-256；本機主金鑰另存 `master.key`。接單程式不把中控台金鑰放進 Agent 的提示詞或資料檔案，檔案系統的訪問範圍由 Agent 權限決定。

## 日誌與確定性

每次被接受的輸入產生一批事實，什麼都沒改變的（重複的事件、距上次不到一分鐘的心跳）不產生；`commit` 在 SQLite WAL + FULL 的同一個交易裡完成判斷、追加日誌並讓 `evolve` 更新檢視，提交完成才應答。規則版本、金鑰雜湊、領活、回條和回答都在日誌裡；日誌從不存輪次 token、卡片連結 token 或中控台主金鑰。主金鑰由外殼儲存在本機檔案，輪次 token 和卡片連結用 HMAC 分別推導。重複 claim 重新簽發 token，上一份立即失效。

`decide(view, input, now, environment)` 不改傳入檢視和輸入。`evolve(view, facts)` 是唯一的持久投影寫入者；時鐘、規則檔案、隨機材料、網路和單一定時器由外殼提供。事實包含版本、序號、時間、種類和規範化記錄變更，重放不重新執行規則。檢視通過 SQLite 索引按需讀取；一次判斷只保留本次改動，不復制整表，不在 JavaScript 中常駐全部歷史。規則這一行最大、每輪排隊都要問，所以一個檢視只解析一次；有了新事實就是新檢視，不會讀到舊規則。日誌、投影、日誌游標、編號高水位及派生索引一起提交；刪掉記錄也不復用其編號。正常啟動直接開啟投影。外殼按決定儲存內容的檔案（`kernel/evolve.ts`、`kernel/credentials.ts`）和主金鑰算格式指紋，別的檔案改動不算，查詢檢視每次啟動重新建；舊版沒有游標或指紋不匹配時，在同一交易內逐條讀取日誌、重建投影和索引，不能覆蓋期間的新提交，不一次把日誌讀進記憶體。首次升級可能需要等待重建；不改舊事實，不需要資料遷移。模擬使用同一套投影和判斷實現，資料庫放在記憶體中。

Node 請求轉換層保持在 50 行內；檔案、SQLite 連線、監聽和定時器也由外殼提供。

`GET /v1/stream?after=42` 僅接受本人的金鑰，返回 SSE：`id` 是日誌序號，`event: fact`，`data` 是事實 JSON。斷線用 `Last-Event-ID` 或 `after` 從下一條繼續；從 0 讀全量，按訂閱者讀取速度逐條傳送，不預先快取全部日誌。不給訂閱者傳送金鑰雜湊或能力憑證。

`GET /v1/runs/42/why` 僅接受本人的金鑰，返回與本輪事件、每次執行的規則版本、領取、回條、卡片回答有關的事實。命令列 `agent-autoloop why 42` 使用同一介面，時間按本機時區顯示為 `MM-DD HH:mm:ss`，預設顯示事件、規則版本、領取者、起止時間、會話、回條、回答和接續輪次的時間線，不印出規則正文；`agent-autoloop why 42 --json` 輸出原始事實。內部回答和定時事件遇到已存在的編號時按序加字尾，保持來源與編號唯一，不覆蓋來源的事件。

## 一致性和復現

外掛入口統一為 `plugins/<名字>/agent.ts`、`channel.ts` 或 `source.ts`，先找安裝目錄，再找引擎內建目錄。`agent-autoloop add <git 地址>` 將外掛倉庫克隆到安裝目錄的 `plugins/<倉庫名>`，倉庫根目錄直接放入口檔案，不自動更新，不執行安裝腳本。目錄名就是外掛名：倉庫名轉成小寫，只能用小寫字母、數字和 `-`，不符合的會被拒絕。外掛是本人安裝的可信程式碼，事件不能指定外掛路徑。

事件接受可選的 `hops`，非負安全整數，預設為 0。回條事件強制使用本輪所有事件最大 hops 加 1；提問的回答和 later 定時延續原深度。超過 8 的事件仍記錄但不派發，併產生通知；重複提交不重複通知。這是中控台內處理鏈的限制，外部來源直接發出的新事件可以從 0 開始。舊日誌沒有 hops 時按 0 讀取。

`DELETE /v1/keys/<source|worker|channel|owner>/<名字>` 只接受本人金鑰；名字按 URL 編碼傳入，返回 `{ok:true, changed}`：要刪的金鑰本來就不存在時 `changed` 為 false，也不追加事實。`agent-autoloop key remove <種類> <名字>` 呼叫正在執行的中控台，刪除立即喚醒並拒絕該金鑰的長輪詢，關閉日誌訂閱。已領取的一輪繼續用獨立的輪次 token 交結果。

`protocol/schema.json` 使用 JSON Schema 2020-12，定義事件、回條、任務、卡片和日誌的格式。`agent-autoloop conformance <測試地址> --config <檔案>` 走真實 HTTP；檔案包含 `keys`（source、worker、channel、owner 四把測試金鑰）、能匹配測試規則的 `eventType` 和通道允許的 `answerer`。規則要能把該來源和型別交給該接單程式，`parallel` 至少為 2，通道要限制回答人。檢查會寫入事件和卡片，只在專用測試中控台執行；同一個測試中控台可以連續檢查。各來源的簽名格式由對應外掛的測試檢查。

文字上限按 Unicode 碼點計算：卡片回答的 `text` 最多 4000 字、`by` 最多 500 字、`ref` 最多 500 字，通道回報的訊息編號最多 500 字。`usage` 必須是數值非負且有限的物件，不能是陣列；`later.at` 必須是真實日期的 ISO 日期時間，帶 `Z` 或時區偏移。回條先核驗整體，再執行。

`npm test` 包含種子 24301 的 200000 步模擬，以及兩台接單程式、兩條來源事件、一張問題卡片的全部 8! 種動作順序。模擬每 128 步換一個獨立場景，每個場景結束前停止故障並把工作處理完；每次狀態轉換都檢查不變數和完整日誌重放。定時事件由真實到期表觸發，恢復後檢查到期任務沒有遺留。它證明這些有限場景，不代表任意大小狀態空間已被窮盡。單獨復現：`node sim/random.ts 24301 200000`、`node sim/enumerate.ts`。

`npm run test:nightly` 做 1000 次真行程 SIGKILL、`sim/mutate.ts` 裡全部的核心變異和效能實測。崩潰用真 SQLite WAL + FULL，核對已確認序號、完整性、檢視、重放和重複提交；它測行程退出，不模擬整機斷電。漏過任何一處變異都算失敗，名字直接輸出，不能用語法錯誤算檢出。CI 每天定時跑一次強殺和變異，效能實測的數字跟機器有關，只在本地跑。`node sim/crash.ts 1000 12648430` 和 `node sim/mutate.ts` 可分別復現。

模擬的正確性檢查必須通過；模擬速度只是開發效率的觀察指標。效能實測使用逐條 HTTP 寫入，交易落盤後才應答。空閒 RSS 和千連線負載 RSS 分開測，實測數字見 README。大歷史量（結果見[歷史增長實測](#歷史增長實測)）用 `node scripts/history.ts 1000 10000 100000` 驗證真實業務、HTTP 響應、慢速日誌訂閱、強殺重試和完整重建；每個場景含兩輪任務、提問、投遞、回答和定時複查，逐筆 WAL + FULL 提交。請求走真實 HTTP，每類操作和狀態彙總都測 30 次取中位數；持續寫入、空閒及請求負載記憶體分別報告，不手動觸發 GC。

排隊很深時的開銷用 `BENCH_QUEUE=5000 node scripts/benchmark.ts --busy` 單獨量：規則約 4.4 KB，1000 個長輪詢等著，排隊 5000 輪（`BENCH_QUEUE` 可改），報告被擋下的心跳 p50 和 p99、每次心跳的 CPU、這段時間寫了多少事實，以及收事件、領活、交結果和領不到活的中位數。`npm run benchmark` 也帶這一項。

### ACP 和 MCP

`use: "acp"` 配合 `command: ["某個 ACP 程式", "啟動參數"]` 使用 stdio ACP v1，ACP Agent 必須寫 `command`，沒寫時這一輪算沒跑成，原因裡寫著缺什麼。橋接先初始化，再新建或接著舊會話：Agent 聲明瞭 `loadSession` 就用 `session/load`，只宣告 `sessionCapabilities.resume` 就用 `session/resume`。載入時重放的歷史不算這一輪的回覆，思考和工具輸出不進回條。提示詞發出去就算這一輪開始了，之後再斷就留在原會話重派。接著舊會話時上一次可能已經幹了一半，只有 Agent 明確拒絕這個會話（回了錯誤，或兩種恢復都不支援）才開新會話；程式起不來、初始化出錯、載入中途斷了都留在原會話重派。會話正被別的程式開啟（錯誤的 `data.reason` 是 `thread_active_writer`）也不算拒絕：這一輪算沒跑成，原因是 Agent 自己的話，留在原會話過一會兒重派，連續第 3 次的卡片會帶上這句話，告訴你要關掉什麼。其他錯誤都算拒絕，不看錯誤碼：官方 Codex 介面卡對真不存在的會話回的是 -32603。只有 `end_turn` 且有最後一條文字訊息才算完成：有 `messageId` 就按它分訊息，沒有時思考、工具呼叫和做完或失敗的工具更新都算分界。一輪沒完成時橋接馬上交代原因，Agent 過 30 秒還不走就連同行程組一起停掉。訊息只按換行分幀，讀不懂的行算這一輪沒跑成。會話編號交給中控台儲存。沒有宣告檔案讀寫、終端機或互動登入能力，Agent 用自己的工具；需要登入時先用它自己的命令列登入。

權限只選一次性的選項：`read` 允許結構化的讀和搜尋，`edit` 再允許工作目錄內的編輯（核對符號連結，經過找不到目標的連結算在目錄外），`full` 允許其他操作。權限請求只帶工具呼叫編號時，按這次呼叫之前說過的種類和路徑判斷，請求自己帶的欄位優先。未提供相應選項就取消。權限依賴 Agent 遵守 ACP，不提供額外的系統隔離；規範允許 Agent 不詢問就執行，這種操作 `access` 攔不住，要用 Agent 自己的模式限制。官方 Codex 介面卡給的拒絕選項（`reject_once`）只有 `cancel`，選了它整輪以 `stopReason: cancelled` 結束，算沒跑成，由中控台重派；`read`、`edit` 檔下要跑命令的請求就是這樣回來的，所以 Agent 非跑命令不可時，給 `full` 或用它自己的模式。`model`、`effort` 不生效。核對依據：[初始化](https://agentclientprotocol.com/protocol/v1/initialization)、[會話](https://agentclientprotocol.com/protocol/v1/session-setup)、[工具權限](https://agentclientprotocol.com/protocol/v1/tool-calls)。

`agent-autoloop mcp` 提供 stdio MCP，固定支援 [2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) 版，不支援 2026-07-28 的無握手協議。工具為 `status`、`why`、`answer`、`resolve`、`stop`、`emit`、`tell`；按本機已有的本人或來源金鑰展示工具。它呼叫同樣的 HTTP 介面，不直接改資料庫；金鑰留在本機 `config.json`。MCP 客戶端把程式設為 `node`，參數設為引擎的絕對路徑 `bin/agent-autoloop.ts` 和 `mcp`，環境裡指定 `AGENT_AUTOLOOP_HOME`。標準輸出只寫 JSON-RPC。訊息只按換行分幀；每個工具呼叫各自回覆，慢呼叫不擋 `ping`。它不區分呼叫方，都按本人記錄（`answer` 記成本人，`emit` 不帶層數），不要配進接單程式啟動的 CLI 的使用者級設定，否則一輪能自己回答自己的卡片。

### 通道範本與命令列示例

Webhook 通道的 `config.json` 設定使用 `use: "webhook"`、`url` 和 `platform`，後者可選 `dingtalk`、`wecom`、`slack`、`discord`。不寫 platform 時可用 `body` 自定義範本，字串裡的 `{text}` 替換為卡片內容。四個範本對照官方文件：[釘釘](https://open.dingtalk.com/document/orgapp/custom-bot-send-message-type)、[企微](https://developer.work.weixin.qq.com/document/path/91770)、[Slack](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/)、[Discord](https://discord.com/developers/docs/resources/webhook#execute-webhook)。企微在標題後顯示建立卡片的規則名，把普通網址顯示為“開啟連結”，把無選項通知的結案地址顯示為“點選處理”，不再另列“1. 已處理”；卡片裡寫的連結標記和尖括號換成全形照字顯示，不會被畫成連結、標籤或提及。釘釘和企微檢查響應的 `errcode`，Slack 檢查 `ok`；Discord 禁止文字觸發提及。超過企微 2048 位元組或 Discord 2000 字的卡片會報告失敗，不截斷問題或回答連結。Webhook 本身沒有冪等保證，訊息傳送成功但報告丟失時可能重發。

Telegram 通道 `telegram` 用 Bot API：`sendMessage` 發純文字（不設 `parse_mode`，別人寫的字不會變成格式）和每個選項一行的按鈕，按鈕的 `callback_data` 是 `卡片:選項`；卡片更新用 `editMessageText` 改原訊息，結束的卡片去掉按鈕，Telegram 說內容沒變時算送達。`ref` 是 `chat:訊息編號`，`by` 是點選人的使用者編號。點選靠 `getUpdates` 長輪詢拿，只要 `callback_query`，下一次請求帶上處理過的編號就是確認；每次點選都 `answerCallbackQuery`，告訴對方記下了沒有。超過 4096 字的卡片報告失敗，不截斷。Telegram 不支援冪等鍵，傳送成功但報告丟失時可能重發。核對依據：[Bot API](https://core.telegram.org/bots/api)。

桌面通知 `desktop` 是新安裝預設開啟的通道：macOS 用 `osascript`，Linux 用 `notify-send`。通知標題是“Agent 問你一個問題”，正文是卡片標題和“執行 agent-autoloop status 檢視”；文字通過 `--` 後的參數傳入，不拼進腳本。沒有圖形會話時不呼叫通知程式，報告 `skipped-<卡片編號>`，不反覆打擾；卡片仍可通過命令列檢視和回答。有圖形會話但通知命令不存在或失敗時報告 `failed`，由中控台安排重試。卡片更新只報告，不重複彈出。

`examples/worker.sh` 和 `examples/channel.sh` 只用 shell 內建命令、curl、jq。設定 `AGENT_AUTOLOOP_URL`、`AGENT_AUTOLOOP_KEY` 後執行；`AGENT_AUTOLOOP_ONCE=1` 只領一次。接單示例交回 `AGENT_AUTOLOOP_RECEIPT` 中的 JSON，預設交回完成；通道示例把卡片輸出到終端機，再報告送達。它們是短任務示例，不適合長任務；長任務使用 `worker/` 的心跳、停止和恢復。`tests/examples.test.ts` 在通過協議一致性檢查的臨時中控台上實際執行兩個腳本，覆蓋提問、送達、回答、繼續和錯誤金鑰。

## 業務場景範本

`examples/recipes/` 提供七套場景。反饋處理、網站巡檢和飛書週報與業務摘要預設使用飛書本人私聊與 `Asia/Shanghai`；都是規則、通道和 `command` 的組合。

反饋來源只負責喚醒同一事項，當前業務狀態和授權從可信介面重新讀取。網站檢查以本規則未關閉的異常通知卡片作為故障記錄：首次失敗發通知及排查事件，持續失敗安靜，恢復結案並行恢復事件；手動關閉未恢復卡片後仍失敗會重新報告。飛書採集完整讀取後寫私有快照並行事件，摘要核對快照編號，舊事件不使用新資料；採集與摘要同組序列。只有本人身份可讀的資料參與彙總，不把不可見當成未提交。

瀏覽器交接範本是主任務對已安裝入口的參數呼叫，不帶瀏覽器驅動。可信設定固定命令、目標與允許操作，續辦使用入口實際返回的 Codex 會話編號；網頁內容和外部事件不能改這些範圍。連線、登入或驗證受阻時由主任務 `ask` 並結束本輪，回答後只繼續剩餘網頁步驟，瀏覽器助手不再次委派或獨立結案。

巡檢和飛書摘要的腳本使用本地假 HTTP 和假飛書 CLI 驗證，不呼叫真實業務資料、不發真訊息。公開樣例不含內部地址、帳號或業務記錄；使用者替換後的資料不應提交到倉庫。

## 結構與實測

一條只追加的事實日誌是業務狀態的來源；檢視可重建，重放不重新執行規則。cron、later、重試、租約和離線判斷共用到期表，外殼只安排下一次到期的定時器。只有改了東西的輸入和到期叫醒的那一次才重算它：什麼都沒改變的輸入（比如被擋下的心跳）不讀排隊，也不寫事實；只隨時間變化的部分都有自己的到期時間，定時器到了自然重算。介面是 HTTP + JSON；專用 CLI、MCP、來源、接單程式和通道都使用同一組介面。

## 交付外掛

交付是 `plugins/delivery` 的普通 Agent 行程，核心不認識它。專案仍用 `ops/delivery.json`，標籤仍是 `deliver`、`deliver-attended`、`deliver-review`、`ask-owner`，提交狀態仍為 `delivery`。審查狀態預設 `agent-review`，由 `review.status` 修改；命令由 `review.command` 修改。設定格式、規則與 Ship 示例見[設定手冊](../skills/agent-autoloop/SKILL.zh-TW.md#交付流水線)。

來源只給事件，倉庫與執行命令由中控台規則固定。內建 `poll.ts` 讀取待處理標籤，以“倉庫、事項、標籤記錄、當前提交”生成穩定事件編號，不另存游標；某個事項讀不到標籤記錄時這一段記 0，不影響其他事項。無標籤（已合併的也一樣）、關閉且未合併、fork 或非 main 目標不啟動交付。每個 PR 一個事項，並行由規則 `parallel` 和接單程式容量控制；行程失敗使用中控台的 5 分鐘起重試和連續失敗通知，不另建佇列、槽位、失敗計數或通知服務。

| 步驟               | 必須滿足                                                                                                                                                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 讀取設定           | 用這一輪審查所對的 main 的固定提交讀專案設定和審查要點，不讀 PR 裡的版本；main 前進後重來一輪就重新讀                                                                                                                                                 |
| 同步               | PR 已包含 main；缺少時請求 GitHub 同步，在本輪內等到同步後的提交出現再繼續，15 分鐘內沒出現才結束這一輪，由中控台重試                                                                                                                                   |
| 審查               | 裸 Git 物件轉文字差異；只審分支自己的提交，排除乾淨合入 main 的變化，保留衝突解決；普通內部文件可略過模型；分支裡有三個及以上父提交的章魚合併時，審檢視不到它帶來的改動，直接報問題，要求改成普通合併                                                 |
| 審查行程           | 不檢出 PR，不執行其中的程式碼、測試、設定或 hooks；預設 Codex 忽略使用者設定和記憶，只讀獨立快照                                                                                                                                                          |
| 完整檢查           | 草稿先轉 ready，轉之前記下最新一次檢查，只接受比它新的（工作流觸發型別要帶 `ready_for_review`）；只接受當前提交最新一次 pull_request 工作流和指定 job 都完成且成功，草稿或 skipped job 不算；矩陣 job（名字像 `check (ubuntu-latest)`）每一項都要成功 |
| 合併               | 再讀 PR head、目標分支、main 和標籤；head 變化或目標分支不再是 main 就結束這一輪，由中控台重試；main 前進就在本輪迴到同步，最多 3 輪；檢查通過後才寫可設定的審查狀態，按已審查 SHA 合併                                                                 |
| 自動合併與響應丟失 | 先關閉已有自動合併並讀回確認；合併響應丟失先看是否已經合併，不盲目再提交；清標籤失敗也讀回確認是否已移除；已合併的 PR 最後去掉 `deliver`，沒合併的最後去掉 `deliver-review`，只去掉一部分時重試能接著做完，也不會把只審查的 PR 合併                   |
| 釋出               | 等一個覆蓋合併提交的 Ship 成功，再核對健康版本；健康 HTTP 200 不能覆蓋 Ship 失敗或尚未完成                                                                                                                                                            |
| 後續釋出           | 新版覆蓋且確實上線可以完成舊交付；已經完成的交付不因後來的失敗釋出倒退                                                                                                                                                                                |

`deliver-review` 審查通過就結束並移除交付標籤，不代表已檢查、合併或上線；在等待檢查期間加上這個標籤，合併前也會停在只審查，不寫允許合併的審查狀態。審查發現問題時 `delivery` 和審查狀態都寫 failure，交回問題；通知卡片按提交分開，上一張沒關也不會吞掉新提交的問題；`deliver-attended` 不額外產生通知卡片。審查狀態是 failure 的提交，標籤還留著時再來事件也不再審查、不改狀態，這一輪直接結束，要推新提交才會重審；這條記錄看審查狀態，因為失敗的一輪會把錯誤寫到 `delivery` 上。等待檢查期間撤回 `deliver`，這一輪結束，`delivery` 寫 success，說明裡寫明已撤回、未合併或釋出。普通 issue 的 `ask-owner` 只將可讀正文變成問題卡片，去掉程式碼塊和本機路徑，答覆後移除標籤。不向 GitHub 發評論，不建立 PR 說明裡的多輪審查賬本，也不支援用“已處理”文字豁免發現的問題；新提交重新審查。

帶 `deliver` 標籤的已合併 PR 直接繼續跟蹤 Ship 和健康檢查，標籤已去掉的不再跟蹤、不寫狀態；審查期間被別人合併的也接著跟蹤；跟蹤失敗時這一輪寫“沒跑成”，由中控台照常重試。預設最多跟蹤 30 分鐘，超時交給中控台重試；沒有健康設定的專案明確報告只完成合並。釋出範圍對比**健康版本到目標提交的整個差異**：只有普通內部文件變化可跳過，可執行位、符號連結、重新命名到外部路徑、未知歷史都要求釋出；後來只有文件變化不能讓尚未完成的程式碼釋出被跳過。健康介面報短提交號時先向 GitHub 換成完整號，換不到就算要釋出。

Ship 使用本引擎倉庫的 `plugins/delivery/action.yml`，專案固定到釋出後的完整提交。Action 只輸出 `release` 和 `superseded`，專案已有釋出步驟根據輸出執行。它與交付行程共用 `project.ts` 的範圍與健康判斷，不在專案里長期複製工具。

普通健康 URL 只允許 HTTPS。測試時必須顯式傳 `--test-local-health`，Action 同樣要 `test-local-health: 'true'`，才接受 `http://127.0.0.1`；不接受其他 HTTP 地址。GitHub 合併規則由專案維護者設定。

## 版本與相容

版本號只寫在 tag 上（`v1.2.3`），不進任何檔案。`agent-autoloop --version` 讀當前提交上的 tag，不在釋出的提交上就顯示“未釋出”。

| 這一版裡影響最大的改動               | 版本號怎麼變              |
| ------------------------------------ | ------------------------- |
| 只修問題                             | 第三位加一：1.1.1 → 1.1.2 |
| 加新能力或改預設行為，老用法照樣能跑 | 第二位加一：1.1.1 → 1.2.0 |
| 老用法不改就跑不了                   | 第一位加一：1.1.1 → 2.0.0 |

老用法指這些：

- `/v1` 介面的路徑、欄位含義和鑑權；
- 外掛約定（`plugins/<名字>/{agent,channel,source}.ts`）；
- `rules.json`；
- 文件寫了的命令和參數；
- 交付約定（`ops/delivery.json`、四個標籤、`delivery` 狀態）；
- 舊版本留下的資料，新版本能接著用。

內部程式碼、文件沒寫的欄位和提示文字不算。新增欄位不算破壞，所以外掛和客戶端要忽略不認識的欄位。要去掉一個東西，先標記廢棄並行一個第二位版本，到下一個第一位版本才真刪。

`/v1` 單獨算：只有 HTTP 介面不相容時才變，軟體到 2.0 不等於協議到 `/v2`。發出去的版本不再改，有問題就發下一個號。

一批改動做完當天發；崩潰、丟資料、安全問題、裝不上的修復當天發；其餘的每週二發。只改文件、測試、CI 的不發。大改動可以先發試用版（`v1.2.0-rc.1`），安裝和 `update` 不會裝到它。
